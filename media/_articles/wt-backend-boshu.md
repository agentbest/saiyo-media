Wantedlyでバックエンドエンジニアの募集記事を出したとき、最初にぶつかるのは「使っている言語とデータベースの名前を書いたのに、話を聞きに来る人が少ない。来ても、面談で『基盤はどこまで自分たちで持っているのか』『設計は誰が決めるのか』を聞かれて答えられない」という問題です。**結論から言うと、バックエンドエンジニアの募集記事は、言語名ではなく「何のデータを、どのくらいの規模で扱っていて、基盤をどこまで自分たちで持っていて、設計を誰が決めるか」を書き、募集記事を書く前に社内でバックエンドの担当範囲を決めておきます。** この記事では、バックエンドエンジニアが募集記事で見ているもの、書く前に決めること、「なにを・なぜ・どうやって」の書き方、技術構成と規模の書き方、「こんな人」の書き方、スカウトと面談への接続、社内の分担、やりがちな失敗を整理します。エンジニア全般の募集記事は[エンジニアを採る募集記事の書き方](/media/wt-engineer-boshu/)で書きました。この記事は、そのうちバックエンドに特有の点を書きます。

## バックエンドエンジニアが募集記事で見ているもの

| 見ているもの | 何を確かめているか |
|---|---|
| 何のデータを扱うか | 注文か、決済か、利用者の情報か、機器から届く記録か。データの種類で、大事にする点が変わる |
| 規模と負荷 | 扱う量と、増え方。夜間に集中するか、常に一定か。数値でなくても、傾向が書いてあるか |
| 基盤をどこまで自分たちで持つか | サーバーや基盤の運用を自分たちでしているか、外部に任せているか。専任の担当がいるか |
| 設計を誰が決めるか | データの構造や仕組みの分け方を、担当者が決めるか、責任者が決めるか |
| 負債と移行の状況 | 古い仕組みが残っているか。分割や移行の途中か。隠さず書いてあるか |
| 障害への向き合い方 | 障害が起きたとき誰が対応するか。夜間や休日の当番があるか。振り返りをしているか |

「基盤をどこまで自分たちで持つか」と「障害への向き合い方」が、バックエンド特有の点です。

## 書く前に決めること｜バックエンドの担当範囲

| 決めること | 選択肢 |
|---|---|
| 基盤の運用 | 自分たちで持つ／外部に任せる／専任の担当がいる |
| 設計を誰が決めるか | 担当者が決めてレビューで確認／責任者が決める／一人目なら誰が支えるか |
| フロントエンドとの境界 | データのやり取りの部分まで／画面も持つ |
| 障害の対応 | 当番があるか。あるなら誰が、どの時間帯か |
| 最初の月に任せること | 一つの機能か、性能の改善か、移行の一部か。誰がレビューするか |

「基盤も持つ」「画面も持つ」「当番がある」という選択でも構いません。隠さずに書けば、それを前提に読む人が来ます。

## 「なにを」｜何のデータを、誰のために

「なにをやっているのか」は、会社の事業ではなく、このバックエンドエンジニアが手を入れる仕組みに絞ります。

- **扱うデータの種類を書く**：「注文と在庫のデータ」「利用者の予約と決済」「機器から届く記録」。データの種類が分かると、何を大事にする開発かが読める
- **誰のための仕組みか**：社外の利用者が使う画面の裏側か、社内の別の部署が使う道具か、他社の仕組みとつなぐ部分か
- **規模と増え方を、傾向で書く**：「一日のうち特定の時間に集中する」「年ごとに増えていて、いまの構造では限界が見えている」。数値は確認できるものだけ

「なにを」の書き方の基本は[「なにをやっているのか」の書き方](/media/wt-boshu-nani-wo/)で書きました。

### エージェントベストの見解

バックエンドエンジニアの募集記事を出す前に、先に決めておかないと効果が出ないのは、「基盤をどこまで自分たちで持つか」と「障害の当番があるか」です。当社がWantedlyのバックエンドの募集を支えるとき、言語とデータベースの名前は揃っているのに、この二つが書かれていない募集記事が多くあります。バックエンドエンジニアが面談で最初に聞くのは、言語の版ではなく、「基盤は誰が見ていますか」「夜間の対応はありますか」です。ここに答えがないと、「基盤の運用も障害対応も、全部一人でやらされる」を想像して離れます。当番があっても構いません。「当番はある。〇人で回していて、夜間は△△の範囲まで。振り返りは□□の形でしている」と書けば、それを前提に読む人が来ます。当社が最初にお願いするのは、技術構成の確認ではなく、「基盤を誰が持ち、障害が起きたら誰が対応するか」の一文です。

## 「どうやって」｜開発の進め方と、技術構成・規模の書き方

### 開発の進め方

| 書くこと | 書き方 |
|---|---|
| 設計を誰が決めるか | データの構造、仕組みの分け方。担当者が決めてレビューで確認するのか、責任者が決めるのか |
| レビュー | 有るか無いか。誰がするか。バックエンドが一人なら、誰がレビューするか |
| テストと監視 | どこまで自動化しているか。何を監視しているか。していないなら、していないと |
| 障害の対応 | 当番の有無、時間帯、振り返りの形 |

書き方の基本は[「どうやっているのか」の書き方](/media/wt-boshu-dou/)で書きました。

### 技術構成と規模

名前の一覧ではなく、選んだ理由と、規模と、移行の状況を書きます。

- **正確に書く**：言語、版、データベース、基盤。バックエンドエンジニアが確認して書く。誤りは一目で分かる
- **選んだ理由を添える**：「〇〇を選んだのは、△△の理由」。「当時いた人が得意だったから」でも正直に
- **規模は、確認できる数値だけ**：扱う量や件数を書くなら、社内で確認した数値だけ。確認できないなら、傾向で書く（「特定の時間に集中する」「年ごとに増えている」）
- **移行や分割の途中なら、そう書く**：「一つの大きな仕組みを、〇〇の単位で分けている途中。新しい機能は分けた側で作り、古い側に手を入れることもある」

## 「こんな人」｜経歴ではなく、行動で書く

| 経歴で書く（避ける） | 行動で書く |
|---|---|
| 〇〇（言語）の経験がある方 | 動いている仕組みに手を入れて、壊さずに変えたことがある |
| 大規模システムの経験 | 遅くなった処理の原因を探して、直したことがある |
| 設計ができる方 | データの構造を、理由を持って決めたことがある。あとで変えやすいように作ったことがある |
| インフラの知識 | 障害が起きたとき、原因を切り分けたことがある（当番の有無を書く） |
| 即戦力 | 最初の月に〇〇の機能を任せる予定です。△△がレビューします |

「最初の月に何を任せ、誰がレビューするか」を書くと、経験年数の条件がいらなくなります。「基盤も持つ」「画面も持つ」を求めるなら、「こんな人」でなく「なにを」と「どうやって」に境界を書きます。書き方の基本は[「こんなことやります」の書き方](/media/wt-boshu-konna/)で書きました。

## スカウトと面談への接続

- **スカウトの文面は、募集記事の「何のデータを、どの規模で」と同じ言葉で**：相手が扱っているデータと仕組みを読み、自社の仕組みと重ねる。言語名を並べない。[エンジニア向けスカウト文面の型](/media/wt-scout-bunmen-rei-eng/)
- **面談には、バックエンドエンジニアが出る**：一人目の募集なら、レビューする人か、基盤を見ている人が出る
- **面談で話すのは、仕組みの話**：いま分割や移行をしている部分の図を見せる、詰まっているところを話す、相手ならどう分けるかを聞く。会社説明を繰り返さない
- **障害の話を隠さない**：最近起きた障害と、どう直したかを話す

つなげ方は[スカウトと募集記事のつなげ方](/media/wt-scout-boshu-renkei/)で書きました。

## 社内の分担

| 作業 | 誰が |
|---|---|
| バックエンドの担当範囲を決める | エンジニアの責任者と人事 |
| 「なにを」（何のデータを、誰のために）の下書き | 人事が、バックエンドエンジニアに聞いて書く |
| 「どうやって」（進め方・技術構成・規模） | バックエンドエンジニアが書く、または人事が聞いて書き、本人が確認 |
| 言語・版・データベース・基盤・数値の確認 | バックエンドエンジニア |
| 障害の当番と振り返りの形 | エンジニアの責任者 |
| 「こんな人」を行動で書く、最初の月の予定 | エンジニアの責任者と人事 |
| 面談 | バックエンドエンジニア（一人目なら、レビューする人か基盤を見ている人） |

一人目のバックエンドエンジニアを採る募集では、「聞く相手」が社内にいません。その場合は、いま仕組みを見ている人（外部の開発会社や、基盤を任せている先）に「いまの仕組みの状態と、詰まっていること」を聞いて書き、「一人目で、設計は〇〇と相談して決める。基盤は△△に任せている」と正直に書きます。

運用代行や代理店が支えられるのは、募集記事の型、技術構成を文で書く直し方、「こんな人」を行動に直す作業、スカウト文面との整合の確認までで、担当範囲の決定、技術構成と数値の正確さ、面談は社内が担います。代理店の代行の範囲は[代理店に運用まで頼めるか](/media/kh-dairiten-unyou/)で書きました。

### エージェントベストの見解

相談で最も多い思い込みは、「バックエンドは規模の大きさを書けば、経験のある人が来る」というものです。当社は3媒体すべての販売パートナーとして、Wantedlyのバックエンドの募集と面談を見ていますが、「大規模」「高負荷」と書いた募集記事に、規模を理由に話を聞きに来た例は多くありません。バックエンドエンジニアが読んでいるのは規模の大きさではなく、「その規模で、何が詰まっていて、それを自分たちで直せる体制か」です。規模だけ書いて体制が書かれていないと、「大きいけれど手が出せない仕組みを、少人数で支えている」を想像して離れます。逆に、規模が小さくても、「いま〇〇が限界で、△△の単位で分けようとしていて、設計は担当者が決められる」と書いてあれば、「自分で決めて直せる」として読まれます。当社が案内するのは、規模を確認できる範囲で正直に書き、そのすぐ後に「何が詰まっていて、誰が決められるか」を書くことです。規模の大きさで人は来ません。詰まっていることと、決められる範囲で来ます。

## やりがちな失敗

| 失敗 | 何が起きるか | 直し方 |
|---|---|---|
| 言語・データベースの名前の一覧で書く | 求人票に見え、読まれない | 何のデータを、どの規模で、なぜその構成で、を文で |
| 基盤の運用と障害の当番を書かない | 面談で聞かれ、答えられない | 誰が持ち、誰が対応するかを書く |
| 確認していない数値を書く | 面談で違いが分かり、信用を失う | 社内で確認した数値だけ。無ければ傾向で |
| 負債と移行を隠す | 面談か入社後に分かり、離れる | 残っていると書き、どうするつもりかを書く |
| 「バックエンド」と書いて、実は画面も基盤も | 面談で「聞いていない」で離れる | 境界を「なにを」と「どうやって」に書く |

最も多いのは、最初の「名前の一覧」です。

## まとめ

- バックエンドエンジニアが見ているのは、何のデータを扱うか・規模と負荷・基盤をどこまで自分たちで持つか・設計を誰が決めるか・負債と移行・障害への向き合い方
- 書く前に、担当範囲（基盤の運用、設計を誰が決めるか、フロントエンドとの境界、障害の当番、最初の月に任せること）を社内で決める。兼務でも当番があっても、隠さず書く
- 「なにを」は扱うデータの種類と、誰のための仕組みか。規模は確認できる数値だけ、無ければ傾向で。「どうやって」は進め方と技術構成を、正確に・理由と一緒に・移行中なら移行中と
- 「こんな人」は言語名ではなく、仕組みに対する行動で。「最初の月に何を任せ、誰がレビューするか」を書く
- 面談にはバックエンドエンジニアが出て、仕組みの図を見せ、障害の話を隠さない

## よくある質問

### 基盤の運用も障害対応も、いまは一人のエンジニアが全部やっています

そのまま書きます。「基盤の運用も障害の対応も、いまは〇〇が一人で見ている。二人目には△△の範囲から分担してもらい、当番は□□の形にする予定」のように、いまの状態と、入った人がどこを担うかを書きます。

### 規模の数値を書きたいのですが、正確な数字がすぐに出ません

確認できるまで、数値は書きません。「特定の時間に集中する」「年ごとに増えていて、いまの構造では限界が見えている」のように、傾向で書きます。数値は、社内のバックエンドエンジニアが確認してから足します。

### バックエンドエンジニアの募集記事は、御社に相談できますか

できます。当社は、募集記事の型、技術構成を文で書く直し方、「こんな人」を行動に直す作業、スカウト文面との整合の確認を支えられます。担当範囲の決定、技術構成と数値の正確さ、面談は、社内で担ってください。当社はOfferBox・Wantedly・ワンキャリアの販売パートナーとして、Wantedlyの募集記事とスカウトの運用を支えています。3媒体の全体像は[3媒体の違いと選び方](/media/hikaku-3baitai/)にまとめています。
