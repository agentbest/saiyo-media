Wantedlyでエンジニアの募集記事を出したとき、最初にぶつかるのは「使っている技術を一覧で書いたのに、話を聞きに来る人が少ない。来ても、面談で『思っていた開発と違う』と言われる」という問題です。**結論から言うと、エンジニア向けの募集記事は、技術名の一覧ではなく「何を作っていて、どう進めていて、いま何を決めようとしているか」を書き、技術構成はその理由と移行の状況まで正確に書き、「こんな人」は経歴ではなく行動で書きます。** この記事では、エンジニアが募集記事で見ているもの、「なにを・なぜ・どうやって」のエンジニア向けの書き方、技術構成の書き方、開発の種類で変える点、「こんな人」の書き方、スカウトと面談への接続、社内の分担、やりがちな失敗を整理します。募集記事の基本構成は[Wantedlyの募集記事の基本構成](/media/wt-boshu-kihon/)、スカウト文面の型は[エンジニア向けスカウト文面の型](/media/wt-scout-bunmen-rei-eng/)で書きました。

## エンジニアが募集記事で見ているもの

エンジニアは多くの募集記事を読み比べていて、事業の説明や「モダンな環境」「裁量が大きい」は読み飛ばします。読まれるのは次の箇所です。

| 見ているもの | 何を確かめているか |
|---|---|
| 何を作っているか | 自分が手を入れる対象は何か。画面か、基盤か、データか。誰が使うものか |
| 使っている技術と、その理由 | 技術名そのものより、なぜそれを選んだか。変えようとしているか |
| 開発の進め方 | チームの人数と役割、レビューの有無、リリースの頻度、設計を誰が決めるか |
| いま詰まっていること | 負債、規模、体制。隠さず書いてあるか |
| 誰と働くか | 同じ職種の人が何人いて、どんな人か。自分より経験のある人がいるか |
| 最初の数ヶ月に何をするか | 入ってすぐ何を任され、誰がレビューするか |

「いま詰まっていること」が書いてある募集記事は少なく、書いてあると「本当のことを書いている会社」として読まれます。

## 「なにを」｜エンジニアが手を入れる対象を、一つに絞る

募集記事の「なにをやっているのか」は、会社全体の事業ではなく、この募集のエンジニアが手を入れる対象に絞ります。

- **作っているものを、一つに絞る**：複数あるなら、この募集で最初に触るものを一つ
- **誰が使うものかを書く**：社外の利用者か、社内の別の部署か
- **いまどの段階か**：作り始めか、育てる段階か、作り直しの途中か
- **エンジニアの言葉で書く**：「顧客体験の向上」ではなく、「注文の画面の表示が遅く、作り直している」

「なにを」の書き方の基本は[「なにをやっているのか」の書き方](/media/wt-boshu-nani-wo/)で書きました。

## 「なぜ」｜技術の選択の理由を書く

エンジニア向けの「なぜやるのか」は、会社の使命の繰り返しではなく、「なぜその技術と進め方を選んだか」を書く場所として使えます。

- **なぜその技術か**：「〇〇を選んだのは、△△の理由」。理由が「流行っていたから」でも、正直に書いたほうが信用される
- **なぜ人を増やすのか**：増員の理由。「事業が伸びているから」だけでなく、「〇〇を作りたいが、いまの人数では△△が回らない」

「なぜ」の書き方の基本は[「なぜやるのか」の書き方](/media/wt-boshu-naze/)で書きました。

### エージェントベストの見解

同じエンジニア採用でも、新卒のエンジニアを採りたい会社にはWantedlyより先にOfferBoxを勧めることが多いです。理由は、新卒の学生は「何を作っているか」の記事を読んで比べるより、企業側から届く文面で会社を知る段階にいることと、学生のプロフィールに書かれた開発の経験を企業側から読んで送るほうが、募集記事を待つより立ち上がりが速いからです。逆に、社会人のエンジニアを採りたい会社には、Wantedlyの募集記事を先に整えることを勧めます。社会人のエンジニアは、自分から募集記事を読み比べて「話を聞きに行く」を選ぶので、募集記事が開発の場面で書かれていないと、スカウトを送っても募集記事で止まります。当社は3媒体すべての販売パートナーなので、「エンジニアだからWantedly」ではなく、「新卒か社会人か」で先に媒体を分け、Wantedlyを使うなら募集記事を先に整える、という順番で案内しています。新卒向けの文面は[OfferBoxでエンジニアを採るオファー文面の書き方](/media/ob-engineer-offer-bunmen/)で書きました。

## 「どうやって」｜開発の進め方と、技術構成の書き方

### 開発の進め方

| 書くこと | 書き方 |
|---|---|
| チームの構成 | 同じ職種が何人か、他の職種（デザイナー・企画）との関係。人数は書ける範囲で |
| 設計を誰が決めるか | 担当者が決めてレビューで確認するのか、責任者が決めるのか |
| レビュー | 有るか無いか。誰がするか |
| リリースの頻度 | 日ごとか、週ごとか、月ごとか。決まっていないなら「決まっていない」 |
| テストと監視 | どこまで自動化しているか。していないなら、していないと書く |

「裁量が大きい」と書くより、「設計は担当者が決め、レビューで確認する」と書くほうが、エンジニアには裁量の大きさが伝わります。書き方の基本は[「どうやっているのか」の書き方](/media/wt-boshu-dou/)で書きました。

### 技術構成

- **正確に書く**：名前、版、構成。エンジニアが確認して書く。誤りは一目で分かる
- **理由を添える**：「〇〇を使っている」だけでなく、「△△のために〇〇を使っている」
- **移行中なら、移行中と書く**：「〇〇から△△に移行中。新しい機能は△△で、既存は〇〇が残っている」。隠すと、面談か入社後に分かる
- **一覧にしない**：技術名を並べるだけの一覧は、検索のための羅列に見える。何のためにどれを使っているかを、文で書く

## 開発の種類で変える点

同じ「エンジニア」の募集でも、自社開発か、受託か、社内システムかで、書くことが変わります。

| 開発の種類 | エンジニアが気にすること | 募集記事に書くこと |
|---|---|---|
| 自社のプロダクト | 何を作っていて、どの段階か。利用者との距離 | プロダクトの段階、利用者の声がどう届くか、作り直しの有無 |
| 受託・請負 | 案件の種類、常駐の有無、案件を選べるか、自社に戻る頻度 | 案件の種類を一つ、常駐の有無と期間、案件がどう決まるか |
| 社内システム | 誰のためのシステムか、外注との分担、自分で作れる範囲 | 使う部署、内製の範囲、外注に出している範囲、決められる範囲 |

受託で常駐の有無を、社内システムで外注との分担を書かないと、面談で「聞いていない」で離れます。書けば、来て離れる人が減ります。

## 「こんな人」｜経歴ではなく、行動で書く

「こんなことやります」「こんな人に来てほしい」は、技術名と経験年数の条件にせず、行動で書きます。

| 経歴で書く（避ける） | 行動で書く |
|---|---|
| 〇〇の経験3年以上 | 動いているものに手を入れて、壊さずに変えたことがある |
| △△の経験がある方 | 使う技術を、理由を持って選んだことがある |
| チーム開発の経験 | 人のコードを読んで直したことがある。レビューで意見を言ったことがある |
| 即戦力 | 最初の月に〇〇を任せる予定です。△△がレビューします |

「最初の数ヶ月に何をするか」を書くと、経験年数の条件がいらなくなります。書き方の基本は[「こんなことやります」の書き方](/media/wt-boshu-konna/)で書きました。

条件（働く場所、勤務の形、待遇）は、隠さず、最後に、短く書きます。[条件をどこまで書くか](/media/wt-boshu-joukenn/)と[待遇をどう扱うか](/media/wt-boshu-kyuuyo/)で書きました。

## スカウトと面談への接続

- **スカウトの文面は、募集記事の「なにを」「どうやって」と同じ言葉で書く**：募集記事に「〇〇を作り直している」と書いたなら、文面にも同じ言葉。文面と募集記事が違うと、「どちらが本当か」と読まれる。[スカウトと募集記事のつなげ方](/media/wt-scout-boshu-renkei/)
- **面談には、同じ職種のエンジニアが出る**：募集記事に書いた「いま詰まっていること」を、面談で本人が話す。
- **面談で話すのは、募集記事の続き**：募集記事で「〇〇を決めようとしている」と書いたなら、面談で「あなたならどうするか」を聞く。会社説明を繰り返さない

募集記事・文面・面談が同じ言葉で書かれていると、話を聞きに来た人が「聞いていた話と同じ」と感じます。

## 社内の分担

| 作業 | 誰が |
|---|---|
| 「なにを」「なぜ」の下書き | 人事が、エンジニアの責任者に聞いて書く |
| 「どうやって」（進め方・技術構成） | エンジニアが書く、または人事が聞いて書き、エンジニアが確認する |
| 技術名・版・構成の確認 | エンジニア |
| 「いま詰まっていること」の一文 | エンジニアの責任者 |
| 「こんな人」を行動で書く、最初の数ヶ月の予定 | エンジニアの責任者と人事 |
| 条件、公開、更新 | 人事 |
| 面談 | 同じ職種のエンジニア |

エンジニアに「書いて」と頼むと止まります。「話して」と頼み、人事が書き、エンジニアが確認する形が続きます。頼み方は[記事づくりに社員の協力を得る方法](/media/wt-shain-kyouryoku/)で書きました。

運用代行や代理店が支えられるのは、募集記事の型、技術構成を文で書く直し方、「こんな人」を行動に直す作業、スカウト文面との整合の確認までで、技術構成の正確さ、詰まっていることの一文、面談は社内のエンジニアが担います。代理店の代行の範囲は[代理店に運用まで頼めるか](/media/kh-dairiten-unyou/)で書きました。

### エージェントベストの見解

エンジニアの募集記事を出す前に、先に決めておかないと効果が出ないのは、「最初の月に何を任せて、誰がレビューするか」です。当社がWantedlyのエンジニア募集を支えるとき、技術構成と事業の説明は揃っているのに、この一つが決まっていない会社が多くあります。決まっていないと、「こんな人」は「〇〇の経験がある方」のような経歴の条件になり、面談では「入ったら何をするか」に答えられず、話を聞きに来た人が「決まっていない会社」と読んで離れます。逆に、「最初の月は〇〇の画面の作り直しを任せ、△△がレビューする」と決まっていれば、「こんな人」は行動で書け、面談では△△本人がその話をでき、スカウトの2段目もその一文になります。募集記事を書く前に、エンジニアの責任者と人事で、この一つだけを決める。当社が最初にお願いするのは、技術構成の一覧ではなく、この一文です。

## やりがちな失敗

| 失敗 | 何が起きるか | 直し方 |
|---|---|---|
| 技術名を一覧で並べる | 求人票に見え、読まれない | 何のために、どれを、なぜ、を文で |
| 古い構成や負債を隠す | 面談か入社後に分かり、信用を失う | 移行中と書き、どうするつもりかを書く |
| 経験年数と技術名で「こんな人」を書く | 自分で判断できず、応募も来ない | 行動と、最初の月の予定で |
| 中途向けをそのまま新卒に出す | 経験の無い読み手に伝わらない | 新卒向けは別に書く。[新卒向け募集記事の書き方](/media/wt-boshu-shinsotsu/) |

最も多いのは、最初の「技術名の一覧」です。並べるだけでは、何のために使っているかが伝わりません。

## まとめ

- エンジニアが募集記事で見ているのは、何を作っているか・技術の理由・開発の進め方・いま詰まっていること・誰と働くか・最初の数ヶ月。会社の事業の説明と抽象語は読み飛ばされる
- 「なにを」はこのエンジニアが手を入れる対象を一つに。「なぜ」は技術の選択の理由。「どうやって」は進め方と技術構成を、正確に・理由と一緒に・移行中なら移行中と
- 自社開発・受託・社内システムで、気にされることが違う。常駐の有無、外注との分担を隠さない
- 「こんな人」は経歴ではなく行動で。「最初の月に何を任せ、誰がレビューするか」を書くと、経験年数の条件がいらなくなる
- 募集記事・スカウト文面・面談を同じ言葉で。面談には同じ職種のエンジニアが出る。新卒のエンジニアは、先にOfferBoxを検討する

## よくある質問

### 使っている技術が古く、正直に書くと来ない気がします

隠すと、面談か入社後に分かって離れます。「〇〇が残っている。△△に移す途中で、新しい機能は△△で作っている」のように、いまの状態と、どうするつもりかを一緒に書きます。移す作業に興味があるエンジニアには、「隠さない会社」として読まれます。

### エンジニアが忙しく、募集記事に協力してもらえません

頼むのは「書くこと」ではなく、「いま何を作っていて、何を決めようとしていて、最初の月に何を任せるか」を話してもらうことです。人事が聞いて書き、技術の言葉だけをエンジニアが確認する形にすれば、エンジニアの時間は話す時間と確認の時間だけになります。技術名と版の確認だけは、省けません。

### エンジニアの募集記事は、御社に相談できますか

できます。当社は、募集記事の型、技術構成を文で書く直し方、「こんな人」を行動に直す作業、スカウト文面との整合の確認を支えられます。技術構成の正確さ、いま詰まっていることの一文、面談は、社内のエンジニアが担ってください。当社はOfferBox・Wantedly・ワンキャリアの販売パートナーとして、新卒か社会人かで媒体を分けるところから案内しています。3媒体の全体像は[3媒体の違いと選び方](/media/hikaku-3baitai/)にまとめています。
