Wantedlyでバックエンドエンジニアにスカウトを送るとき、最初にぶつかるのは「自社と同じ言語で検索して送っているのに、返信が来ない。来ても、面談で『基盤は誰が見ているのか』『当番はあるのか』を聞かれて止まる」という問題です。**結論から言うと、バックエンドエンジニアへのスカウトは、言語名の一致で相手を選ぶのではなく、先に自社のバックエンドの担当範囲と最初に任せる仕組みを決め、「同じ種類のデータを、同じくらいの規模の段階で扱っている人」を選び、その人が扱っている仕組みを読んだ一文から、自社の仕組みの場面で誘います。** この記事では、バックエンドエンジニアがスカウトで見ているもの、送る前に決めること、誰に送るか、文面に書くこと、返信後の面談、社内の分担、やりがちな失敗を整理します。エンジニア全般のスカウトの考え方は[エンジニアにスカウトを送る文面の考え方](/media/wt-engineer-scout/)、文面の3段の型は[エンジニア向けスカウト文面の型](/media/wt-scout-bunmen-rei-eng/)、募集記事は[バックエンドエンジニアを採る募集記事の書き方](/media/wt-backend-boshu/)で書きました。

## バックエンドエンジニアがスカウトで見ているもの

| 見ているもの | 何を確かめているか |
|---|---|
| 誰から来たか | 送り主がバックエンドエンジニアか、人事か。送り主が何の仕組みを見ているか |
| 自分の何を読んだか | 言語名で検索しただけか、扱っているデータや書いた記事を読んだか |
| 何のデータを扱う会社か | 注文か、決済か、記録か。自分が手を入れる仕組みの種類 |
| 基盤と障害対応の範囲 | 基盤を自分たちで持つか。当番があるか。文面で分かるか |
| 設計を誰が決めるか | 担当者が決められるか、責任者が決めるか |
| 話す場か、応募の依頼か | 仕組みの話をする場に呼ばれているのか、応募を求められているのか |

「基盤と障害対応の範囲」は、書かれていなければ面談で最初に聞かれます。

## 送る前に決めること｜担当範囲と、最初に任せる仕組み

送る前に、社内で二つを決めます。

- **バックエンドの担当範囲**：基盤の運用を自分たちで持つか、設計を誰が決めるか、フロントエンドとの境界、障害の当番の有無。決め方は[バックエンドエンジニアを採る募集記事の書き方](/media/wt-backend-boshu/)で書きました
- **最初に任せる仕組み**：「最初の月は〇〇の処理の改善を任せ、△△がレビューする」を一つ。これが文面の2段目になり、送る相手を「それができる人」に絞れる

## 誰に送るか｜言語の一致ではなく、データの種類と規模の段階の重なり

言語が同じでも、扱っているデータの種類と規模の段階が違えば、面談で「うちの仕組みとは違う」になります。選ぶ基準は、「同じ種類のデータを、同じくらいの規模の段階で扱っているか」です。

| 読む箇所 | 重なりの見方 |
|---|---|
| 何のデータを扱っているか | 注文・決済・予約・記録など、データの種類。自社が任せる仕組みと同じ種類か。種類が近いと、大事にする点（正確さ、速さ、量）が近い |
| 規模の段階 | 小さく作り始めた段階か、増えて限界が見えた段階か、分割や移行をした段階か。自社のいまの段階と重なるか |
| 何を直したか | 遅くなった処理を直した、構造を変えた、分割した、障害の原因を切り分けた。自社の「最初に任せる仕組み」と重なるか |
| 基盤との関わり | 基盤も見ているか、開発だけか。自社の分担と合うか |
| 書いている記事 | 仕組みの設計や障害の振り返りを書いていれば、何を大事にする人かが分かる |

「規模の段階」が要点です。自社が「増えて限界が見え、分割しようとしている」段階なら、同じ段階を経験した人か、いま同じ段階にいる人。「小さく作り始めた」段階なら、一人で仕組み全体を作った経験のある人。言語名は「あればよい条件」に置きます。絞り方の基本は[スカウト対象の絞り方](/media/wt-scout-target/)で書きました。

### 書いている記事の読み方

バックエンドエンジニアは、仕組みの設計や障害の振り返りを記事にしている人が一定数います。あれば読み、文面で「〇〇についての記事の、△△の判断の部分を読みました」と一文で触れます。記事の結論ではなく、「なぜそう判断したか」の部分に触れると、読んだことが伝わります。書いていない人を外しません。

### エージェントベストの見解

言語名で検索して出てくる人の数は、「自社の仕組みの話を聞きに来る人の数」ではありません。当社がWantedlyのバックエンド向けスカウトを支えるとき、「〇〇（言語）で検索すると多く出るので、そこから送ります」と言われることがありますが、その数には、扱っているデータの種類が自社と違う人、規模の段階が違う人（小さく作る段階の人に、分割の話をしても重ならない）、基盤も含めて一人で見ている人と開発だけの人が混ざっています。言語名で出た数をそのまま送る数にすると、送る手間に対して返信が少なく、「Wantedlyはバックエンドに効かない」という結論になりがちです。当社が案内するのは、言語名で出た数を「母数」として扱い、そこから「データの種類が同じ」「規模の段階が近い」「基盤との関わりが自社の分担と合う」で絞り、絞った数だけを送ることです。送る数は減りますが、面談で「うちの仕組みとは違う」になる人がいなくなります。

## 文面に書くこと

文面の型（相手の一文→自社の開発の場面→話す場の案内）は[エンジニア向けスカウト文面の型](/media/wt-scout-bunmen-rei-eng/)に書いたので、ここではバックエンド特有の要点だけを書きます。

- **相手の一文は、仕組みで**：「〇〇のデータを扱う仕組みを作られていると書かれていたのを読んで」「△△についての記事の、□□の判断の部分を読みました」。言語名ではなく、データと、その仕組みで何を大事にしていたか
- **担当範囲を、最初のほうで**：「基盤は〇〇に任せていて、開発に集中してもらいます」「基盤も自分たちで持っていて、当番は△△の形です」。隠さない
- **最初に任せる仕組みを、一文で**：「最初の月は〇〇の処理の改善を任せ、△△がレビューします」。募集記事と同じ言葉
- **いま決めようとしていることを、一つ**：「一つの大きな仕組みを、〇〇の単位で分ける順番を、いま決めようとしています」。会社説明ではなく、仕組みの場面
- **規模は、確認できる数値だけ**：数値を書くなら社内で確認したものだけ。無ければ「特定の時間に集中する」「年ごとに増えている」の傾向で
- **話す場は、バックエンドエンジニアと**：「同じ職種の〇〇と、いま分けようとしている仕組みの図を見ながら話します。転職を決めていなくても構いません」

相手の技術を評価しません。

## 返信後の面談｜仕組みの図を見せる

画面と違って見て分かるものが無いので、図が無いと会社説明に戻ります。

| 話すこと | 中身 |
|---|---|
| 自社の仕組みの図を見せる | いま分割や移行をしている部分、詰まっている部分。全体でなく、任せる部分の周辺 |
| 相手ならどう分けるか | 見せた図について、相手の考えを聞く。ここが長い面談ほど次につながる |
| 担当範囲の確認 | 基盤を誰が持つか、設計を誰が決めるか、当番の有無と時間帯。ここで「聞いていない」を出さない |
| 最近の障害と、どう直したか | 隠さない。振り返りの形を話す |
| 最初に任せる仕組み | 誰がレビューするか。レビューする本人が話す |
| 相手の仕組みの話 | 相手が何のデータをどう扱っていて、何を直したか。聞く時間を長く |

面談には、バックエンドエンジニアが出ます。一人目の募集なら、レビューする人か、基盤を見ている人が出ます。面談の設計は[カジュアル面談の設計](/media/wt-scout-casual-mendan/)で書きました。

選考に進むとき、設計や実装の課題を出すなら、面談のときに「課題がある」「どのくらいの時間がかかるか」を先に伝えます。伝え方は[カジュアル面談から選考に進むときの伝え方](/media/wt-scout-senkou-ikou/)で書きました。

## 社内の分担

| 作業 | 誰が |
|---|---|
| 担当範囲と、最初に任せる仕組みを決める | エンジニアの責任者と人事 |
| 「データの種類と規模の段階」で対象を並べ直す | 人事（バックエンドエンジニアが基準を伝える） |
| 相手の仕組みや記事を読み、一文を書く | バックエンドエンジニア（または人事が下書きし、本人が確認） |
| 技術の言葉と数値の確認 | バックエンドエンジニア |
| 型、送信、返信対応、台帳 | 人事 |
| 面談（仕組みの図を見せる） | バックエンドエンジニア（一人目なら、レビューする人か基盤を見ている人） |

一人目のバックエンドエンジニアを採るスカウトでは、「読んで一文を書く人」が社内にいません。その場合は、いま仕組みを見ている人（外部の開発会社や、基盤を任せている先）に相手のプロフィールを見てもらい、「一人目で、設計は〇〇と相談して決める。基盤は△△に任せている」と正直に文面に書きます。

運用代行や代理店が支えられるのは、対象の並べ直しの基準づくり、型、避ける言葉のチェック、募集記事との整合の確認までで、担当範囲の決定、相手の仕組みを読んだ一文、技術の言葉と数値の確認、面談は社内が担います。代理店の代行の範囲は[代理店に運用まで頼めるか](/media/kh-dairiten-unyou/)で書きました。

### エージェントベストの見解

相談で最も多い思い込みは、「バックエンドは言語が同じ人でないと、入ってすぐ動けない」というものです。当社は3媒体すべての販売パートナーとしてWantedlyのスカウトを見ていますが、バックエンドエンジニアが返信した文面を並べると、言語名が一致していたかどうかは、返信の有無とほとんど関係がありません。関係があるのは、「自分が扱っているデータと仕組みを読んでくれたか」と、「基盤を誰が持ち、当番があるかが文面で分かるか」の二つです。言語が一致していても、相手が小さく作り始めた段階の人で、自社が分割の途中なら、面談で「経験していない段階」になります。逆に、言語が違っても、同じ種類のデータを同じ段階で扱った人なら、「言語は入ってから覚える」で話が進みます。当社が対象を組み直すとき、最初にやるのは、検索条件から言語名を外し、「何のデータを、どの段階で扱っている人か」で並べ直し、担当範囲を文面の最初のほうに入れることです。

## やりがちな失敗

| 失敗 | 何が起きるか | 直し方 |
|---|---|---|
| 言語名の一致で相手を選ぶ | 面談で「段階が違う」「仕組みが違う」 | データの種類と規模の段階で選ぶ |
| 基盤と当番の範囲を文面で隠す | 面談で「基盤は誰が」で止まる | 最初のほうで分かるように書く |
| 確認していない数値を文面に書く | 面談で違いが分かり、信用を失う | 社内で確認した数値だけ。無ければ傾向で |
| 面談で図を見せず、会社説明をする | 仕組みの話ができず、終わる | 任せる部分の周辺の図を見せる |
| 課題を後から出す | 「聞いていない」で離れる | 面談で先に伝える |

最も多いのは、最初の「言語名の一致で選ぶ」です。

## まとめ

- バックエンドエンジニアは、誰から来たか・自分の何を読んだか・何のデータを扱う会社か・基盤と障害対応の範囲を、文面の段階で見ている
- 送る前に、担当範囲（基盤の運用、設計を誰が決めるか、境界、当番）と、最初に任せる仕組みを決める
- 誰に送るかは、言語の一致ではなく、扱っているデータの種類と規模の段階の重なりで。「何を直したか」を読む。記事はあれば「なぜそう判断したか」の部分に触れ、無くても外さない
- 文面には、相手の仕組みを読んだ一文、担当範囲、最初に任せる仕組み、いま決めようとしていることを。数値は確認できるものだけ。相手の技術を評価しない
- 面談は仕組みの図を見せ、最近の障害を隠さず話す。バックエンドエンジニアが出る。課題を出すなら先に伝える

## よくある質問

### 自社と同じ言語を使っている人が、検索でほとんど出ません

言語で絞る必要はありません。「同じ種類のデータを、同じくらいの規模の段階で扱っている人」で選び、文面に「使っている言語は違いますが、〇〇のデータを△△の段階で扱われている点が、うちのいまの状況と近いと思い」と書きます。

### 基盤の運用も当番も、いまは一人で全部やっています。文面にそう書くと来ませんか

隠すほうが、面談で「聞いていない」で離れます。「基盤の運用も当番も、いまは〇〇が一人で見ている。二人目には△△の範囲から分担してもらい、当番は□□の形にする予定」と書けば、それを前提に読む人だけが返信します。数は減りますが、面談で離れる人がいなくなります。

### バックエンド向けのスカウトの対象の絞り込みは、御社に相談できますか

できます。当社は、対象の並べ直しの基準づくり、文面の型、避ける言葉のチェック、募集記事との整合の確認を支えられます。相手の仕組みを読んだ一文、技術の言葉と数値の確認、面談は、社内のバックエンドエンジニアが担ってください。当社はOfferBox・Wantedly・ワンキャリアの販売パートナーとして、Wantedlyのスカウト運用を支えています。3媒体の全体像は[3媒体の違いと選び方](/media/hikaku-3baitai/)にまとめています。
