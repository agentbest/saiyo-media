Wantedlyでフロントエンドエンジニアの募集記事を出したとき、最初にぶつかるのは「使っているフレームワークの名前を書いたのに、話を聞きに来る人が少ない。来ても、『デザインは誰が決めるのか』『どこまでが自分の担当か』を聞かれて答えられない」という問題です。**結論から言うと、フロントエンドエンジニアの募集記事は、フレームワーク名ではなく「どの画面を、誰のために、デザイナーやバックエンドとどう分担して作るか」を書き、募集記事を書く前に社内でフロントエンドの担当範囲を決めておきます。** この記事では、フロントエンドエンジニアが募集記事で見ているもの、書く前に決めること、「なにを・なぜ・どうやって」の書き方、技術構成の書き方、「こんな人」の書き方、スカウトと面談への接続、社内の分担、やりがちな失敗を整理します。エンジニア全般の募集記事は[エンジニアを採る募集記事の書き方](/media/wt-engineer-boshu/)で書きました。この記事は、そのうちフロントエンドに特有の点を書きます。

## フロントエンドエンジニアが募集記事で見ているもの

技術の入れ替わりが速い職種なので「いまどの技術か」は見ますが、それ以上に見ているのは「自分の担当がどこからどこまでか」です。

| 見ているもの | 何を確かめているか |
|---|---|
| どの画面を、誰のために作るか | 社外の利用者が使う画面か、社内の管理画面か。画面の種類と数 |
| デザイナーとの分担 | デザインは誰が決めるか。デザイナーがいるか。実装者がデザインをどこまで変えられるか |
| バックエンドとの境界 | 画面だけか、データのやり取りの部分まで持つか。「フルスタック」を求められるか |
| 表示の速さ・使いやすさをどこまで任されるか | 遅い画面を直す、使いにくい画面を直すのを、自分で決めて動けるか |
| 技術の選択と、移行の状況 | なぜそのフレームワークか。古い画面が残っているか。移行の途中か |
| 開発の進め方 | レビュー、テスト、リリースの頻度。デザインの確認の流れ |

「デザイナーとの分担」と「バックエンドとの境界」が、フロントエンド特有の点です。

## 書く前に決めること｜フロントエンドの担当範囲

募集記事を書く前に、社内で「フロントエンドの担当範囲」を決めます。

| 決めること | 選択肢 |
|---|---|
| デザインを誰が決めるか | 社内のデザイナー／外部のデザイナー／フロントエンドエンジニアが兼ねる |
| デザインをどこまで変えられるか | 渡されたとおりに作る／使いにくい点は提案して変える／自分で決める |
| バックエンドとの境界 | 画面のみ／データのやり取りの部分まで／バックエンドも持つ |
| 一人目か、何人目か | 一人目なら、設計の決め方を誰が支えるか |

「フロントエンドエンジニアが兼ねる」「バックエンドも持つ」でも構いません。隠さずに書けば、それを前提に読む人が来ます。決まっていないまま「フロントエンド」と書き、面談で「実はバックエンドも」と出るのが、最も離れる形です。

## 「なにを」｜どの画面を、誰のために

「なにをやっているのか」は、会社の事業ではなく、このフロントエンドエンジニアが手を入れる画面に絞ります。

- **画面の種類を書く**：社外の利用者が使う画面か、社内の管理画面か、両方か。「〇〇を注文する画面」「△△の担当者が毎日使う管理画面」
- **誰が、どう使うかを書く**：使う人と、使う場面。「初めて使う人が、一度で申込を終えられるように」「一日に何度も開く人が、迷わないように」
- **いまの状態を書く**：作り始めか、動いている画面を育てる段階か、作り直しの途中か。「古い画面が残っていて、順に作り直している」
- **利用者の反応が、どう届くか**：問い合わせ、利用者の声

「なにを」の書き方の基本は[「なにをやっているのか」の書き方](/media/wt-boshu-nani-wo/)で書きました。

### エージェントベストの見解

フロントエンドエンジニアの募集記事を出す前に、先に決めておかないと効果が出ないのは、「デザイナーとの分担」です。当社がWantedlyのフロントエンドの募集を支えるとき、技術構成は詳しく書かれているのに、デザインを誰が決めるかが書かれていない募集記事が多くあります。フロントエンドエンジニアが面談で最初に聞くのは、フレームワークの版ではなく、「デザインは誰が決めますか」「使いにくいと思ったら変えられますか」です。ここに答えがないと、「デザイナーがいない会社で、デザインも自分でやらされる」か、「渡されたとおりに作るだけ」のどちらかを想像して、離れます。デザイナーがいなくても構いません。「デザイナーはいない。いまは〇〇が画面の案を作り、フロントエンドエンジニアが使いやすさの観点で変えている」と書けば、それを前提に読む人が来ます。当社が最初にお願いするのは、フレームワークの確認ではなく、「デザインを誰が決めて、実装者がどこまで変えられるか」の一文です。

## 「どうやって」｜開発の進め方と、技術構成の書き方

### 開発の進め方

フロントエンド特有の点は、「デザインの確認の流れ」です。

| 書くこと | 書き方 |
|---|---|
| デザインの確認の流れ | デザイン案をどこで受け取り、実装したものを誰が確認するか |
| レビュー | 有るか無いか。誰がするか。フロントエンドが一人なら、誰がレビューするか |
| テストとリリース | 画面の動きの確認をどこまで自動化しているか。画面の変更をどのくらいの間隔で出しているか |
| 表示の速さ・使いやすさの改善 | 誰が課題を見つけ、誰が優先順位を決めるか |

書き方の基本は[「どうやっているのか」の書き方](/media/wt-boshu-dou/)で書きました。

### 技術構成

名前の一覧ではなく、選んだ理由と移行の状況を書きます。

- **正確に書く**：フレームワーク、版、周辺の道具。フロントエンドエンジニアが確認して書く。誤りは一目で分かる
- **選んだ理由を添える**：「〇〇を選んだのは、△△の理由」。「流行っていたから」でも正直に
- **移行中なら、移行中と**：「古い画面は〇〇で作られていて、新しい画面から△△に移している。古い画面に手を入れることもある」
- **バックエンドの技術も、境界とともに**：「データのやり取りは□□で、フロントエンドは△△の部分まで持つ」

## 「こんな人」｜経歴ではなく、行動で書く

「こんなことやります」「こんな人に来てほしい」は、フレームワーク名と経験年数の条件にせず、行動で書きます。

| 経歴で書く（避ける） | 行動で書く |
|---|---|
| 〇〇（フレームワーク）の経験がある方 | 使う人の動きを見て、画面を直したことがある |
| デザインへの理解 | デザインの意図を読んで、実装で解いたことがある。デザイナーに提案したことがある |
| フルスタック志向 | データのやり取りの部分まで、自分で作ったことがある（境界を書く） |
| 自走できる方 | 最初の月に〇〇の画面を任せる予定です。△△がレビューします |

「最初の月に何を任せ、誰がレビューするか」を書くと、経験年数の条件がいらなくなります。「フルスタック」を求めるなら、「こんな人」でなく「なにを」と「どうやって」に境界を書きます。書き方の基本は[「こんなことやります」の書き方](/media/wt-boshu-konna/)で書きました。

公開している成果物（自分で作った画面、書いた記事）を求める書き方は、「あれば見せてほしい」にとどめます。「必須」にすると、会社の仕事で作ったものを公開できない人が離れます。

## スカウトと面談への接続

- **スカウトの文面は、募集記事の「どの画面を、誰のために」と同じ言葉で**：相手が作っている画面を読み、自社の画面と重ねる。技術名を並べない。[エンジニア向けスカウト文面の型](/media/wt-scout-bunmen-rei-eng/)
- **面談には、フロントエンドエンジニアとデザイナーが出る**：デザイナーがいるなら、面談に出ると「分担」が言葉でなく実際に伝わる。一人目の募集なら、レビューする人が出る
- **面談で話すのは、画面の話**：いま作り直している画面を見せる、詰まっているところを話す、相手ならどう直すかを聞く。会社説明を繰り返さない

つなげ方は[スカウトと募集記事のつなげ方](/media/wt-scout-boshu-renkei/)で書きました。

## 社内の分担

| 作業 | 誰が |
|---|---|
| フロントエンドの担当範囲を決める | エンジニアの責任者、デザイナー、人事 |
| 「なにを」（どの画面を、誰のために）の下書き | 人事が、フロントエンドエンジニアに聞いて書く |
| 「どうやって」（進め方・技術構成） | フロントエンドエンジニアが書く、または人事が聞いて書き、本人が確認 |
| フレームワーク・版・構成の確認 | フロントエンドエンジニア |
| デザインの確認の流れ | デザイナー |
| 「こんな人」を行動で書く、最初の月の予定 | エンジニアの責任者と人事 |
| 面談 | フロントエンドエンジニア（一人目なら、レビューする人）とデザイナー |

一人目のフロントエンドエンジニアを採る募集では、「聞く相手」が社内にいません。その場合は、いま画面を作っている人（バックエンドのエンジニアや、外部の制作会社）に「いまの画面の状態と、詰まっていること」を聞いて書き、「一人目で、設計は〇〇と相談して決める」と正直に書きます。

運用代行や代理店が支えられるのは、募集記事の型、技術構成を文で書く直し方、「こんな人」を行動に直す作業、スカウト文面との整合の確認までで、担当範囲の決定、技術構成の正確さ、面談は社内が担います。代理店の代行の範囲は[代理店に運用まで頼めるか](/media/kh-dairiten-unyou/)で書きました。

### エージェントベストの見解

相談で最も多い思い込みは、「フロントエンドは、使っているフレームワークが一致する人を採らないと、すぐに動けない」というものです。当社は3媒体すべての販売パートナーとして、Wantedlyのフロントエンドの募集と面談を見ていますが、フレームワークが一致しているかどうかで、入社後の立ち上がりに大きな差が出た例は多くありません。差が出るのは、「使う人の動きを見て画面を直した経験があるか」と、「デザイナーやバックエンドと分担して作った経験があるか」です。フレームワークは入れ替わりが速く、いま一致していても、次の移行で変わります。フレームワーク名を「こんな人」の条件にすると、その名前で検索して来る人だけに絞られ、画面を直した経験のある人を落とします。当社が案内するのは、フレームワーク名を「あればよい条件」に置き、「こんな人」は画面に対する行動で書き、面談で「どう直したか」を聞くことです。

## やりがちな失敗

| 失敗 | 何が起きるか | 直し方 |
|---|---|---|
| フレームワーク名の一覧で書く | 求人票に見え、読まれない。名前で検索した人だけが来る | どの画面を、誰のために、なぜその技術で、を文で |
| デザイナーとの分担を書かない | 面談で聞かれ、答えられない | 誰が決め、どこまで変えられるかを書く |
| 「フロントエンド」と書いて、実はバックエンドも | 面談で「聞いていない」で離れる | 境界を「なにを」と「どうやって」に書く |
| 一人目なのに、チームがあるように書く | 入ってから「一人だった」 | 一人目と書き、誰が支えるかを書く |
| 公開している成果物を必須にする | 会社の仕事で作った人が離れる | 「あれば見せてほしい」にとどめる |

最も多いのは、最初の「フレームワーク名の一覧」です。

## まとめ

- フロントエンドエンジニアが見ているのは、どの画面を誰のために作るか・デザイナーとの分担・バックエンドとの境界・技術の選択と移行・表示の速さや使いやすさをどこまで任されるか
- 書く前に、フロントエンドの担当範囲（デザインを誰が決めるか、どこまで変えられるか、バックエンドとの境界）を社内で決める。決めた内容が兼務でも、隠さず書く
- 「なにを」は画面の種類と使う人。「どうやって」はデザインの確認の流れと技術構成を、正確に・理由と一緒に・移行中なら移行中と
- 「こんな人」はフレームワーク名ではなく、画面に対する行動で。「最初の月に何を任せ、誰がレビューするか」を書く
- 面談にはフロントエンドエンジニアとデザイナーが出て、画面の話をする。一人目の募集は、一人目と書き、誰が支えるかを書く

## よくある質問

### デザイナーがいません。フロントエンドエンジニアにデザインも見てほしいのですが

そのまま書きます。「デザイナーはいない。いまは〇〇が画面の案を作り、フロントエンドエンジニアが使いやすさの観点で変えている。デザインの判断に関わりたい人に向いている」のように、いまの状態と、どこまで関わるかを書きます。

### 古いフレームワークで作った画面が多く、正直に書くと来ない気がします

隠すと、面談か入社後に分かって離れます。「古い画面は〇〇で作られていて、新しい画面から△△に移している。古い画面に手を入れることもある」と、いまの状態と方針を書きます。移行の作業に興味がある人には、「隠さない会社」として読まれます。

### フロントエンドエンジニアの募集記事は、御社に相談できますか

できます。当社は、募集記事の型、技術構成を文で書く直し方、「こんな人」を行動に直す作業、スカウト文面との整合の確認を支えられます。担当範囲の決定、技術構成の正確さ、面談は、社内で担ってください。当社はOfferBox・Wantedly・ワンキャリアの販売パートナーとして、Wantedlyの募集記事とスカウトの運用を支えています。3媒体の全体像は[3媒体の違いと選び方](/media/hikaku-3baitai/)にまとめています。
