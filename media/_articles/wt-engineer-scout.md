Wantedlyでエンジニアにスカウトを送るとき、最初にぶつかるのは「使っている技術で検索して、その技術名を文面に入れて送っているのに、返信が来ない。来ても、面談で『うちの開発とは違う』となる」という問題です。**結論から言うと、エンジニアへのスカウトは、技術名の一致で相手を選ぶのではなく、先に自社の開発の種類（自社のプロダクトか、受託か、社内システムか）と任せる範囲を決め、その開発と「作っているもの・進め方」が重なる人を選び、その人の作っているものを読んだ一文から、自社の開発の場面で誘います。** この記事では、エンジニアがスカウトで見ているもの、送る前に決めること、誰に送るか、文面に書くこと、返信後の面談、社内の分担、やりがちな失敗を整理します。文面の3段の型そのものは[エンジニア向けスカウト文面の型](/media/wt-scout-bunmen-rei-eng/)で書いたので、この記事では「誰に、何を前提に送るか」を中心に書きます。募集記事は[エンジニアを採る募集記事の書き方](/media/wt-engineer-boshu/)で書きました。

## エンジニアがスカウトで見ているもの

| 見ているもの | 何を確かめているか |
|---|---|
| 誰から来たか | 送り主がエンジニアか、人事か。エンジニアなら、その人が何を作っているか |
| 自分の何を読んだか | 技術名を検索しただけか、作っているものや書いたものを読んだか |
| 何を作っている会社か | 自分が手を入れる対象は何か。自社のプロダクトか、受託か |
| 開発の場面 | いま何を作っていて、何を決めようとしているか。募集記事と同じ言葉か |
| 話す場か、応募の依頼か | 開発の話をする場に呼ばれているのか、応募を求められているのか |

「誰から来たか」が最初です。送り主がエンジニアで、その人のプロフィールに作っているものが書いてあると、開かれる率が変わります。送り主を現場社員にする方法は[スカウトを現場社員の名前で送る方法](/media/wt-scout-genba/)で書きました。

## 送る前に決めること｜自社の開発の種類と、任せる範囲

スカウトを送る前に、社内で二つを決めます。

### 自社の開発の種類

| 種類 | 送る相手が気にすること |
|---|---|
| 自社のプロダクト | 何を作っていて、どの段階か。利用者との距離。作り直しがあるか |
| 受託・請負 | 案件の種類、常駐の有無と期間、案件を選べるか |
| 社内システム | 誰のためか、外注との分担、自分で作れる範囲 |

### 任せる範囲

「最初の月に何を任せて、誰がレビューするか」を一つ決めます。これが決まると、送る相手は「それができる人」に絞れ、文面の2段目（自社の開発の場面）はその一文になり、面談ではレビューする本人がその話をできます。

## 誰に送るか｜技術名の一致ではなく、作っているものと進め方の重なり

エンジニアへのスカウトで最も多い失敗は、自社が使っている技術名で検索し、一致した人に送ることです。技術は変わるので、いま一致していることより、「作っているもの」と「進め方」が重なっているかで選びます。

| 読む箇所 | 重なりの見方 |
|---|---|
| 何を作っているか | 自社が任せる対象と、同じ種類のものを作っているか。画面か、基盤か、データか。誰が使うものか |
| 技術の使い方 | 技術名ではなく、その技術で何をしたか、なぜ選んだか。自社の選び方と近いか |
| 開発の進め方 | チームで作っているか、一人で作っているか。レビューやリリースの頻度について書いているか |
| やりたいこと | 「次は〇〇を作りたい」が、自社の開発の次の段階と重なるか |

### 相手のいまの環境で、読み方を変える

同じ「エンジニア」でも、いまどの種類の開発をしているかで、自社の開発をどう読むかが変わります。

- **自社のプロダクトを作っている人**：利用者との距離と、開発の進め方を比べる。「作っているものの種類」と「段階」が重なる人に
- **受託で開発している人**：自社のプロダクトを持つ会社への転職を考えている人が多い一方、「一つのものを長く育てる」経験が無い場合がある。任せる範囲を「最初は〇〇の機能から」と具体に
- **社内システムを作っている人**：外注の管理が中心だった人と、自分で作っていた人が混ざる。プロフィールの「自分で作った」の記述で見分ける
- **新卒・経験の浅い人**：作っているものより「何を学んでいて、何を作ってみたか」で読む。任せる範囲と、誰が教えるかを文面に。新卒の考え方は[新卒にスカウトを送るときの考え方](/media/wt-scout-shinsotsu/)

技術名で絞るのは、最後です。「作っているもの」と「進め方」で選び、技術名は「あればよい条件」に置きます。絞り方の基本は[スカウト対象の絞り方](/media/wt-scout-target/)で書きました。

### エージェントベストの見解

相談で最も多い思い込みは、「自社と同じ技術を使っている人に送れば、返信が来る」というものです。当社は3媒体すべての販売パートナーとしてWantedlyのスカウトを見ていますが、返信が来る文面と来ない文面を並べると、技術名が一致しているかどうかは、ほとんど関係がありません。関係があるのは、「相手が作っているものと、自社が任せるものが、同じ種類か」と、「文面が、自社の開発の種類（自社のプロダクトか、受託か）を隠していないか」の二つです。技術が一致していても、相手が一人で作っている人で、自社がチームでレビューしながら作る会社なら、面談で「進め方が違う」になります。逆に、技術が違っても、作っているものの種類と進め方が近ければ、「その技術は入ってから覚えられる」で話が進みます。当社が対象を組み直すとき、最初にやるのは、検索条件から技術名を外し、「何を作っている人か」で並べ直すことです。

## 文面に書くこと

文面の型（相手の一文→自社の開発の場面→話す場の案内）は[エンジニア向けスカウト文面の型](/media/wt-scout-bunmen-rei-eng/)に書いたので、ここでは職種別の要点だけを書きます。

- **自社の開発の種類を、最初のほうで分かるように**：「自社のプロダクトを作っています」「受託で、〇〇の案件が中心です」「社内の△△の部署が使うシステムです」。隠さない
- **任せる範囲を、一文で**：「最初の月は〇〇の機能を任せ、△△がレビューします」。募集記事と同じ言葉
- **いま決めようとしていることを、一つ**：「〇〇の設計を、△△と□□で迷っています」。会社説明ではなく、開発の場面
- **相手の技術を評価しない**：「〇〇のご経験を活かして」は、技術名で検索したと分かる。「〇〇を△△のために使われている点を読んで」
- **話す場は、同じ職種のエンジニアと**：「転職を決めていなくても、開発の話をするだけで構いません」

文面の長さと件名は[スカウト文面の長さの目安](/media/wt-scout-nagasa/)と[スカウトの件名の付け方](/media/wt-scout-kenmei/)で書きました。

## 返信後の面談で話すこと

返信が来たら、面談は同じ職種のエンジニアが出ます。話すのは、文面の続きです。

| 話すこと | 中身 |
|---|---|
| 文面に書いた開発の場面 | 「〇〇を決めようとしている」の詳細。あなたならどうするか、を聞く |
| 任せる範囲 | 最初の月に何をするか。誰がレビューするか。レビューする本人が話す |
| いま詰まっていること | 負債、規模、体制。隠さない |
| 相手の開発の話 | 相手が何を作っていて、どう進めているか。聞く時間を長く |
| 開発の種類の確認 | 受託なら常駐の有無と期間。社内システムなら外注との分担。ここで「聞いていない」を出さない |

「いま詰まっていること」を話すと、相手は自分ならどうするかを話し始めます。面談の設計は[カジュアル面談の設計](/media/wt-scout-casual-mendan/)で書きました。

面談のあと、選考に進むときの伝え方は[カジュアル面談から選考に進むときの伝え方](/media/wt-scout-senkou-ikou/)で書きました。エンジニアの場合、選考に課題を出すなら、面談のときに「課題がある」と先に伝えます。後から出すと、「聞いていない」になります。

## 社内の分担

| 作業 | 誰が |
|---|---|
| 自社の開発の種類と、任せる範囲を決める | エンジニアの責任者と人事 |
| 「作っているもの」で対象を並べ直す | 人事（エンジニアが基準を伝える） |
| 相手のプロフィールを読み、重なる点を書く | エンジニア（または人事が下書きし、エンジニアが確認） |
| 技術の言葉の確認 | エンジニア |
| 型、送信、返信対応、台帳 | 人事 |
| 面談 | 同じ職種のエンジニア。レビューする本人 |

エンジニアの時間を、「基準を伝える」「読んで一文を書く」「面談」に限ると続きます。絞り込み、型、送信、台帳は人事が持ちます。分担の考え方は[スカウトを誰が送るか](/media/wt-scout-tantou/)で書きました。

運用代行や代理店が支えられるのは、対象の並べ直しの基準づくり、型、避ける言葉のチェック、募集記事との整合の確認までで、開発の場面の一文、技術の言葉の確認、面談は社内のエンジニアが担います。代理店の代行の範囲は[代理店に運用まで頼めるか](/media/kh-dairiten-unyou/)で書きました。

### エージェントベストの見解

技術名で検索して出てくる人の数は、「自社の話を聞きに来る人の数」ではありません。当社がWantedlyのエンジニア向けスカウトを支えるとき、「〇〇で検索すると多く出るので、そこから送ります」と言われることがありますが、その数には、いまの環境に満足していて動く意思の無い人、作っているものの種類が自社と違う人、一人で作っていてチームの進め方と合わない人が混ざっています。技術名で出た数をそのまま送る数にすると、送る手間に対して返信が少なく、「Wantedlyはエンジニアに効かない」という結論になりがちです。当社が案内するのは、技術名で出た数を「上限」ではなく「母数」として扱い、そこから「作っているものの種類が同じ」「進め方が近い」「動く意思が読める」で絞り、絞った数だけを送ることです。送る数は減りますが、面談につながる数は減りません。

## やりがちな失敗

| 失敗 | 何が起きるか | 直し方 |
|---|---|---|
| 技術名の一致で相手を選ぶ | 技術は変わる。面談で「進め方が違う」 | 作っているものと進め方で選ぶ |
| 自社の開発の種類を文面で隠す | 面談で「聞いていない」で離れる | 最初のほうで分かるように書く |
| 任せる範囲を決めずに送る | 返信が来ても面談で答えられない | 「最初の月に何を任せ、誰がレビューするか」を先に決める |
| 人事だけで書いて送る | 技術の言葉の誤りが一目で分かる | エンジニアが確認する |
| 面談に人事だけが出る | 開発の話ができず、終わる | レビューする本人が出る |
| 募集記事と文面の言葉が違う | 「どちらが本当か」と読まれる | 同じ言葉で書く。[スカウトと募集記事のつなげ方](/media/wt-scout-boshu-renkei/) |

最も多いのは、最初の「技術名の一致で選ぶ」です。検索の条件がそのまま文面の言葉になります。

## まとめ

- エンジニアは、誰から来たか・自分の何を読んだか・何を作っている会社か・話す場か応募の依頼か、を見ている。送り主はエンジニア
- 送る前に、自社の開発の種類（自社のプロダクト・受託・社内システム）と、「最初の月に何を任せ、誰がレビューするか」を決める
- 誰に送るかは、技術名の一致ではなく、作っているものと進め方の重なりで。相手のいまの環境（自社開発・受託・社内システム・新卒）で読み方を変える
- 文面には、開発の種類を隠さず、任せる範囲と決めようとしていることを一文で。相手の技術名を並べない
- 面談は同じ職種のエンジニアが出て、詰まっていることを隠さず話し、相手の開発の話を長く聞く。課題を出すなら面談で先に伝える

## よくある質問

### 自社と同じ技術を使っている人が、検索でほとんど出ません

技術名で絞る必要はありません。「作っているものの種類」と「進め方」で選び、技術は「入ってから覚える」前提で文面に書きます。「〇〇を作られていて、うちも同じ種類のものを作っています。使っている技術は違いますが、進め方が近いと思い」のように書くと、技術が違っても話す理由になります。

### 受託の会社です。自社開発の会社に比べて、返信が来にくいのではないですか

受託であることを隠すと、来にくくなります。「受託で、〇〇の案件が中心です。常駐は△△です」と最初のほうで書き、その上で「この案件の□□を、あなたの作っているものを読んで任せたい」と書くと、受託を前提に読んでくれる人だけが返信します。数は減りますが、面談で「聞いていない」で離れる人がいなくなります。

### エンジニア向けのスカウトの対象の絞り込みは、御社に相談できますか

できます。当社は、対象の並べ直しの基準づくり、文面の型、避ける言葉のチェック、募集記事との整合の確認を支えられます。開発の場面の一文、技術の言葉の確認、面談は、社内のエンジニアが担ってください。当社はOfferBox・Wantedly・ワンキャリアの販売パートナーとして、Wantedlyのスカウト運用を支えています。3媒体の全体像は[3媒体の違いと選び方](/media/hikaku-3baitai/)にまとめています。
