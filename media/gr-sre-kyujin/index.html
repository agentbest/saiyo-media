Greenでインフラエンジニア・SREを採る求人票｜仕事内容と条件の書き方

Green・IT中途採用職種別の求人票 更新日 2026/11/4

インフラエンジニアやSREの求人票では、クラウドのサービス名や監視の道具の名前が並びがちです。けれど候補者が最も気にしているのは、道具の名前より「入社したら、作る仕事と守る仕事がどのくらいの割合で来るのか」と「夜や休日に呼ばれることがあるのか」です。結論から言うと、Greenでインフラエンジニア・SREを採る求人票は、構築と運用の比重、オンコールの体制、開発チームとの分担の三つを正直に書くと、入社後のずれが減り、合う人が応募しやすくなります。 Greenは株式会社アトラエが運営する、IT・Web業界を中心とした中途採用の求人サイトです。この記事では、インフラ・SREの求人票を項目ごとに型と例文で整理します。入力欄の名前や表示のされ方は、管理画面と媒体の案内で確認してください。

インフラ・SREの候補者が求人票で確かめること

インフラ・SREの候補者は、求人票を読みながら、次の点を確かめています。

  • 構築と運用の比重：新しい基盤を作る仕事が中心か、いまある基盤を守る仕事が中心か
  • オンコールと障害対応：夜間や休日の呼び出しがあるか、何人で分担しているか
  • 手作業の量：定型の作業がどのくらい残っていて、自動化する余地があるか
  • 開発チームとの関係：開発チームが自分たちで運用まで担うのか、インフラ・SREが受け持つのか
  • 判断の権限：構成や監視の仕組みを、チームで決められるか
  • いまの課題：止まりにくさ、費用、移行など、何に取り組んでいるか

職種全体の考え方はGreenでインフラエンジニアやSREを採るときの要点で整理しています。この記事では、求人票の各欄に何をどう書くかに絞ります。

求人タイトルと冒頭の一文

タイトルには、支えている基盤と、いま取り組んでいることを入れます。

  • 弱い例：「インフラエンジニア／クラウド／リモート可」
  • 直した例：「予約サービスの基盤を、止まりにくく作り直すSRE／監視と自動化から担当」

直した例は、何を支えていて、何を変えたいのか、入社した人がどこから始めるのかが一行で伝わります。

冒頭の一文には、いま困っていることを書きます。「サービスの成長に運用の手が追いつかず、障害のたびに同じ人が対応している状態を変えたいと考えています」のように書くと、運用を仕組みで良くすることに関心のある人が読み進めます。

職種名は、「インフラエンジニア」と「SRE」のどちらを使うかで、届く人が変わることがあります。どちらの名前を使う場合も、仕事内容の欄で「何をする仕事か」を具体的に書いておけば、名前の違いによるずれは小さくなります。

インフラ・SREの求人票で、運用の範囲やオンコールをどう書くか。現場の話を聞くところから一緒に整理します。

運用の相談をする

仕事内容の書き方｜型と例文

仕事内容の欄は、次の順で書きます。

  1. 支えている基盤：どのサービスの基盤か、クラウドか自社の設備か、その組み合わせか
  2. 構築と運用の比重：いまと今後を分けて書く。「いまは運用が中心で、来期から基盤の作り直しに取り組む」
  3. 手作業と自動化の状況：どんな作業が手作業で残っていて、どこまで仕組みにしたいか
  4. 入社後の最初の仕事：最初の数か月で担当する範囲
  5. 半年後に任せたいこと：構成の見直しの方針づくり、監視の仕組みの整備など

例文にすると、次のような形になります。

飲食店向けの予約サービスを支える基盤を担当します。基盤はクラウドの上にあり、いまは日々の運用と障害対応が仕事の中心です。リリースの手順や設定の変更には手作業が多く残っていて、ここを仕組みにしていくことがチームの課題です。入社後は、監視の見直しと、手作業の手順を自動化するところから始めていただきます。慣れてきたら、基盤の構成を見直す方針づくりを、リーダーと一緒に進めていただきたいと考えています。

この型で書くと、「いまは運用が多い」ことと「これから変えていく」ことの両方が伝わります。運用の多さを隠して「新しい基盤の構築」だけを書くと、入社した人が早く離れる原因になります。

エージェントベストの見解

インフラ・SREの求人票の相談で多い思い込みは、「運用が多いと書くと、応募が来なくなる」というものです。実際には、運用の改善や自動化に関心のある人は、運用の課題が書かれている求人に反応します。避けられやすいのは、運用の量そのものより、「運用が多いのに、変える気配がない」と読める求人です。同じ運用中心の仕事でも、「手作業の手順がこれだけ残っていて、ここから仕組みにしたい」と変えたい方向が書いてあれば、候補者は自分の仕事として受け取れます。当社は媒体での採用と紹介での採用の両方を見ていますが、インフラ・SREの候補者が紹介の面談で最初に確かめるのも、この「運用の量」と「変える余地」です。求人票で先に答えておくと、面談の時間を、どう変えていくかという具体的な話に使えます。

オンコールと開発チームとの分担の書き方

インフラ・SREの求人票で、書く会社と書かない会社で差が出るのが、オンコールと分担です。

オンコールの体制は、次の点を書きます。

  • オンコールがあるかどうか
  • 何人で、どんな順番で回しているか
  • 呼び出しの頻度の考え方（数値を出せなくても、「月に数回あるかどうか」「障害の少ない時期はほぼない」のように言葉で）
  • 手当や代休の扱い
  • 呼び出しを減らすために、いま取り組んでいること

開発チームとの分担は、どこまでを開発チームが持ち、どこからをインフラ・SREが持つかを書きます。「開発チームが自分たちのサービスの監視と一次対応を持ち、SREは基盤と仕組みづくりを受け持つ」のように書くと、候補者は自分の役割を想像できます。分担がまだ決まっていないなら、「分担を一緒に決めていきたい」と書くのも一つの方法です。

必須と歓迎、条件と選考の流れ

求める経験は、必須を二つか三つに絞ります。

  • 必須の例：「Webサービスの基盤の運用の実務経験」「障害の切り分けと対応の経験」
  • 歓迎の例：「手作業の手順を自動化した経験」「構成をコードで管理した経験」「開発チームと分担を決めた経験」

特定のクラウドの経験を必須にするなら、その理由を添えます。設計や運用の考え方は共通する部分も多いので、理由がなければ「別のクラウドや自社の設備での経験でも構いません」と書くと、応募の幅が広がります。

条件の欄には、給与の幅と決め方、リモートの可否と出社の考え方を書きます。インフラ・SREでは、障害対応のときに出社が必要になるかどうかも、候補者が気にする点です。給与の書き方はGreenの求人票の年収の書き方で整理しています。

選考の流れには、各回で誰と何を話すかを書きます。とくに、選考のどこかで現場の人からオンコールの実際を説明する場を設けると、候補者は入社後の負担を自分で判断できます。

求人票の作成から応募への返信、日程調整まで、作業の部分を外に出す形もあります。相談だけでも構いません。

エージェントベストの見解

インフラ・SREの求人を出したあとによく起きるのは、応募が来ても「構築の仕事をしたい人」と「運用を良くしたい人」が混ざり、面接で期待のずれが表に出ることです。このずれは、求人票の「構築と運用の比重」の欄で、いまと今後を分けて書いていないときに起きやすくなります。勧めているのは、面接に出る現場のリーダーに、入社後の最初の半年で「作る仕事」と「守る仕事」がどう来るかを、週単位の例で書いてもらうことです。たとえば「週の前半は運用の当番と改善、後半は自動化の作業」のように書けば、候補者は自分の一週間を想像できます。この例は求人票にもスカウトにも使えます。スカウトの書き方はインフラエンジニア・SREへ送るスカウト文面にまとめています。

まとめ

  • インフラ・SREの求人票は、構築と運用の比重、オンコール、開発チームとの分担を正直に書く
  • タイトルと冒頭で、支えている基盤といまの課題、入社後に始める仕事を伝える
  • 運用が多いことは隠さず、変えたい方向と一緒に書く
  • オンコールは体制・頻度の考え方・手当・減らす取り組みまで書く
  • 構築と運用の比重は、いまと今後を分け、週単位の例で伝える

よくある質問

オンコールがあることを書くと、応募が減りませんか

一時的に減ることはあるかもしれませんが、入社後に知って離れる人を防げます。体制や分担、呼び出しを減らす取り組みも合わせて書くと、負担の大きさだけが伝わることを避けられます。

インフラエンジニアとSREで、求人を分けるべきですか

仕事の中身が違うなら分けて構いません。同じ仕事を別の名前で呼んでいるだけなら、一つの求人で、仕事内容の欄に何をするかを具体的に書くほうが分かりやすくなります。

自社の設備での運用が中心です。クラウドの経験者に向けて書けますか

書けます。いまの構成と、今後クラウドに移す予定があるかどうかを正直に書きます。移す予定がない場合でも、運用の改善や自動化の余地を書けば、関心を持つ人はいます。
